# 数据库建议：PostgreSQL，初期优先 Supabase Free

结论：推荐使用 PostgreSQL 作为关系数据库，初期可选择 Supabase 免费托管。它适合机构、项目、语言轨道、申请轮次、招聘、证据和三语译文的关系及版本约束。Supabase 是托管与配套服务，数据库本身仍是 PostgreSQL。

## 本项目的省钱方案

1. 初期单个 Supabase 项目保存结构化事实、必要证据摘录、来源哈希、译文和审核记录。
2. 大型原始 HTML、PDF、截图不进 Postgres。采集期放本地 work/raw，重要证据另行压缩备份；未来对象存储根据真实用量选择。
3. 三种语言用同一数据库；事实只存一份，译文按 entity_id + locale + source_version 唯一约束。不要建三个数据库。
4. 公网站读取三语发布快照／服务端缓存；避免每次切换语言都直连数据库拉全表。采用分页、按需详情、共享缓存。
5. 初期不启用 Realtime、向量库、短信登录、独立收费搜索、数据库自定义域名或额外计算项目。
6. 匿名搜索无需登录，收藏先用本地存储。审核后台才需要账号；后续需要跨设备同步再实现用户 Auth 与按用户隔离。
7. 定期检查表、索引、审计与日志空间。以 350 MB 作为内部容量复核阈值，450 MB 前完成升级或归档方案；这些是项目预警策略，不是官方限额。
8. Free 不含自动备份：至少每周、每次批量发布前做可恢复逻辑导出并保存在数据库外；定期实际恢复验证。发布 JSON 快照不是完整数据库备份。

500 MB 是否够不能只看记录条数，应导入一批真实三语数据后测平均记录、索引和历史版本占用。对于第一阶段文字型目录，它是合理起点，但不承诺固定可容纳多少项目。

## 暂停和中国大陆访问

Free 更适合原型和试运行。数据库暂停时，静态快照可继续展示，但新数据更新、登录与写入会不可用；前台必须显示最后更新时间，并根据现有截止日期计算失效状态。
缓存无法掩盖源数据长期不更新。正式运营且依赖持续更新时，应预算 Pro 或其他可靠托管方案，不用虚假保活替代正式可用性方案。

Supabase 当前官方地区包含新加坡、东京、法兰克福等，未列中国大陆地区。优先根据网站服务端所在位置和实测选区，不能凭“新加坡较近”保证国内访问。
地区来源：https://supabase.com/docs/guides/platform/regions 。
建议公网站经自身服务端／缓存读取 Supabase；这减少浏览器对第三方域名的直接依赖，但不能保证跨境链路质量，也不能替代备案或网络实测。
如目标是内地服务器部署且严格要求内地数据与访问，应重新评估内地托管 PostgreSQL。第一版不收集护照或申请材料，减少不必要数据负担。

## 数据访问约束

草稿、源材料和审核日志不得放入匿名可读接口；公开读只指向已发布快照。
若使用 Supabase 客户端直接访问表，必须为暴露表配置并测试 RLS；服务端管理密钥绝不放前端。
采用 PostgreSQL 迁移脚本和稳定外键；事实、译文、审核、发布在事务中绑定版本，保留将来迁移到普通 PostgreSQL 的能力。

## 备选取舍

- 仅本地 SQLite + 静态输出：没有云数据库费，适合单人本地维护；多人审核、远程管理及同步需要另建服务。
- 自建 PostgreSQL：软件免费，但服务器、备份、安全更新和运维都要承担；初期不必为省小额费用增加这部分工作。
- Supabase Free → Pro：本项目默认建议，成本与工程投入较平衡。正式开通和付费留待实施阶段。
